# AI Radar — Build Plan

## Context

`~/ai-radar` is an empty repo (one commit: `.gitignore` + a stub README). The goal is a
daily AI-news digest built as a real data pipeline — ingest ~14 sources, deduplicate,
score each item against a personal interest profile with an LLM, and deliver 8–12 items
to Telegram every morning. It doubles as a portfolio piece demonstrating ELT, incremental
loading, data-quality tests, and cost-conscious LLM integration.

This document is the build plan of record. It derives from an earlier design spec, corrects
what live probing proved wrong (see the next section), resolves the open decisions, and
sequences the work so something runs at the end of every session.

**Status:** nothing implemented yet — Phase 0 is the next action.

**How to use this file:** work one phase per session, one commit per phase. Do not skip
ahead; the temptation to build the pretty part first is what kills this kind of project.
When driving an agent, point it at this file rather than describing the task in chat.

## Findings that change the spec

Probed live during planning — these are verified, not assumed:

| Finding | Consequence |
|---|---|
| `anthropic.com/rss.xml` → **404**. So are `/news/rss.xml`, `/feed.xml`, `/engineering/rss.xml`, `/research/rss.xml` | Anthropic has no public feed. **Drop `anthropic_news`.** Their launches arrive via HN + Simon Willison anyway. |
| `openai.com/blog/rss.xml` works but redirects | Use the canonical `https://openai.com/news/rss.xml` |
| `reddit.com/r/*/new.json` → **403** even with a descriptive User-Agent | Unauthenticated Reddit is dead. **OAuth client-credentials required** (decided: build it). |
| 10 of 11 remaining feeds return 200 with entries | `sources.yaml` is otherwise sound |
| HN Algolia + GitHub search work unauthenticated | No credentials needed for either |
| Global `dbt` is **dbt-fusion 2.0.0-preview**, not dbt-core | Pin `dbt-core` + `dbt-duckdb` in the project venv; never invoke the global binary |
| Python 3.14.7; dlt 1.30 requires `<3.15` | Compatible. Pin `requires-python = ">=3.10,<3.15"` |
| `https://api.z.ai/api/anthropic/v1/messages` → 401 (exists, needs key) | GLM exposes an **Anthropic-compatible endpoint** — the same `anthropic` SDK works with a `base_url` swap |

Two more corrections to the spec's code:

- Model ID is **`claude-haiku-4-5`** — current Claude IDs carry no date suffix. The spec's
  `claude-haiku-4-5-20251001` should not be copied forward.
- The spec's `int_items_dedup.sql` mixes `row_number()`/`max()`/`string_agg()` window
  functions with a `select * except(rn)` in one CTE. `string_agg` is BigQuery syntax;
  DuckDB needs `string_agg(source_name, ',')`. Write dialect-portable SQL or gate with
  `{{ target.type }}`.

## Decisions resolved

1. **Enrichment: provider-swappable, GLM first.** One `EnrichmentBackend` interface, two
   implementations. Start free on GLM; flip to Claude Haiku + Batch API via config if
   GLM's JSON reliability or score quality disappoints. This is also the better portfolio
   story — "I abstracted the provider and measured both" beats either alone.
2. **Reddit: build it with OAuth.** Script app + client-credentials token flow.
3. **Warehouse: DuckDB for dev, BigQuery for prod.** User has a GCP project and service
   account already.
4. **Anthropic RSS: dropped.** No feed exists.
5. **Delivery: three renderers over one table.** Telegram first (Phase 4), then Gmail SMTP
   and a static GitHub Pages archive (Phase 5). Not Outlook, not Streamlit — see below.

### Delivery channels — why these three

`fct_daily_digest` is just rows. Delivery is N renderers over the same query, sharing one
`build_digest()` that returns structured items; each channel formats them its own way. This
is the same abstraction shape as the enrichment backends.

| Channel | Verdict | Why |
|---|---|---|
| **Telegram** | Primary | No auth flow, no domain, no deliverability problems. One HTTP POST. Read over coffee. |
| **Gmail SMTP** | Yes, Phase 5 | App passwords **still work in 2026** (needs 2FA on). ~10 lines of `smtplib`, free, no domain. Gives you a searchable archive in a place you already live. |
| **Static HTML → GitHub Pages** | Yes, Phase 5 | Generated by the same Actions run, pushed to `gh-pages`. Never sleeps, zero credentials, zero cold start, permanent portfolio URL. Accumulates into the archive Phase 6 RAG needs. |
| **Outlook / Microsoft 365** | ❌ Blocked | Microsoft **permanently disabled Basic Auth for SMTP AUTH on 1 March 2026**. Outlook.com personal accounts cannot enable SMTP AUTH at all, and app passwords no longer work. OAuth2 only — far too much machinery for a cron job. |
| **Streamlit Community Cloud** | ❌ Not for this | Free-tier apps **sleep after 12h without traffic**. A once-daily digest site is asleep almost every time anyone opens it — visitors get a "get this app back up" button and a cold start. Also needs a second copy of the GCP key in Streamlit's secrets. |
| **Resend** | Later, optional | 3,000/mo but **100/day** and requires one verified sending domain. Fine if a custom domain appears; unnecessary friction versus Gmail for self-delivery. |

The instinct that "sending an HTTP request is a bad idea" isn't the real issue — BigQuery at
~200 rows/day is free and fast. What rules Streamlit out is the sleeping app and the extra
credential copy. Streamlit becomes the *right* answer at Phase 6, when interactive search
over the archive genuinely needs a running server; static HTML can't do that.

```
14 sources ─dlt→ raw.items ─dbt→ stg_items → int_items_dedup
                                                   │
                                    ┌──────────────┘
                                    ▼
                          enrich (GLM | Claude) → raw.enrichments
                                    │
                                    ▼
                          dbt → fct_items → fct_daily_digest
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
               Telegram        Gmail SMTP     static HTML
              (primary)         (mirror)      → GitHub Pages
                    └───────────────┴───────────────┘
                                    │
                                    ▼
                          raw.sent_items ledger

```

## Phase 0 — Walking skeleton (~2h)

**Goal: one feed → DuckDB → your phone buzzes.** No dbt, no LLM.

- `uv init`; deps: `dlt[duckdb]`, `feedparser`, `httpx`, `pyyaml`, `anthropic`, `pytest`
- Append to `.gitignore`: `*.duckdb`, `.env`, `*-sa.json`, `transform/target/`,
  `transform/logs/`, `.dlt/secrets.toml` — **before the first commit**, not after
- `ingest/normalize.py` — `canonicalize()` + `url_hash()` exactly as specced
- `tests/test_normalize.py` — the arXiv-variant collapse test, plus `www.`, trailing
  slash, protocol, and tracking-param cases. **Write these before the resource.**
- `ingest/sources/rss.py` — generic `@dlt.resource`, wired to arXiv cs.CL only.
  `_parse_date` must return **tz-aware UTC**; a naive datetime silently breaks the
  dlt incremental cursor.
- Telegram bot via @BotFather; send 5 titles read back from DuckDB

**Done when:** one command, five arXiv titles on your phone. Ugly is correct here.

## Phase 1 — Real ingestion (~3h)

- `config/sources.yaml` — the corrected list:
  - **arXiv** cs.CL (1.0), cs.LG (0.9), cs.AI (0.9)
  - **Labs**: `openai.com/news/rss.xml` (1.5), `deepmind.google/blog/rss.xml` (1.4),
    `research.google/blog/rss/` (1.2), `blog.google/technology/ai/rss/` (1.2),
    `huggingface.co/blog/feed.xml` (1.2)
  - **Practitioners**: `simonwillison.net/atom/everything/` (1.3),
    `magazine.sebastianraschka.com/feed` (1.3)
  - **Aggregators**: HN Algolia (0.7), `lobste.rs/t/ai.rss` (0.8), Reddit r/LocalLLaMA (0.6)
  - **Repos**: GitHub search (0.8)
  - No `anthropic_news` — the feed does not exist
- `ingest/pipeline.py` — dispatch table + **fail-soft**: one dead source must never cost
  the digest. Collect `(name, error)` and surface in the message footer.
- HN Algolia: map `points`/`num_comments` into `engagement`. HN items have two URLs —
  canonicalize the **story** link, keep the HN discussion link in `discussion_url`.
- GitHub: use the Actions-injected `GITHUB_TOKEN` (30 req/min vs 10).
- **Reddit OAuth** (new work vs. spec):
  - Register a *script* app at reddit.com/prefs/apps → `REDDIT_CLIENT_ID` / `REDDIT_CLIENT_SECRET`
  - `POST https://www.reddit.com/api/v1/access_token`, HTTP Basic auth with
    `client_id:secret`, body `grant_type=client_credentials`
  - Then read `https://oauth.reddit.com/r/LocalLLaMA/new?limit=100` with
    `Authorization: Bearer <token>` **and** a descriptive `User-Agent`
  - Tokens expire (~1h); fetch one per run, cache in memory. Wrap the whole source so a
    Reddit outage or credential expiry fails soft.
- `scripts/validate_feeds.py` — run it; delete or fix anything that 404s

**Done when:** all sources land in DuckDB, and a **second consecutive run adds ~0 rows.**
Verify the incremental cursor by hand — this is where generated code looks right and isn't.

## Phase 2 — dbt (~3h)

- `dbt-core` + `dbt-duckdb` **in the project venv** (`uv run dbt`), not the global fusion binary
- `stg_items` (view) — trim/filter, guard future timestamps and epoch-0 parses
- `int_items_dedup` (incremental, `unique_key='url_hash'`) — one row per hash, earliest
  sighting, max engagement, `corroboration = least(source_count, 3)`.
  Use `string_agg(source_name, ',')` for DuckDB portability.
- `fct_items` — join `raw.enrichments`, compute `final_score` (enrichment columns null for now)
- Tests: `unique` + `not_null` on `url_hash`, `accepted_range` on `relevance_score`,
  `accepted_values` on `category`

**The `unique` test on `int_items_dedup.url_hash` will fail the first time.** That failure
is the real work of this project — fix `canonicalize()` until it passes. Every duplicate
that escapes later becomes a new case in `tests/test_normalize.py`. **Never loosen the test.**

**Done when:** `dbt build` green, and `count(int_items_dedup)` meaningfully below `count(raw.items)`.

## Phase 3 — Enrichment (~3h)

**`config/profile.yaml` first, written honestly.** It goes into the prompt verbatim and
drives every score. Spend real time here.

**Provider abstraction:**

```
enrich/backends/base.py    EnrichmentBackend: enrich(items, profile) -> list[dict]
enrich/backends/glm.py     anthropic.Anthropic(base_url="https://api.z.ai/api/anthropic",
                             api_key=GLM_API_KEY) + bounded concurrency (~5 workers)
enrich/backends/claude.py  anthropic.Anthropic() + messages.batches.create/results
```

Selected by `ENRICH_BACKEND=glm|claude`. Both return the same dict shape, so `run.py` and
everything downstream are provider-agnostic.

- **One item per request** — never batch multiple items into one prompt; cross-item
  contamination makes scores drift.
- Prompt returns `{summary, category, entities, relevance_score, reason}`. The `reason`
  field costs almost nothing and is how you debug bad rankings.
- **Pre-filter before spending anything**: inside the 26h window, not already in
  `raw.enrichments`, plus cheap heuristic cuts (title length, non-English).
- Parse defensively — strip ``` fences, `try/except` per item, skip on failure, **log the
  malformed-JSON rate**. That rate is the number that decides GLM vs Haiku.
- Batch path (`claude.py`): results arrive in **any order** — key by `custom_id = url_hash`,
  never by position.
- Write to `raw.enrichments`, keyed on `url_hash`, separate from raw data so prompts can be
  re-run and diffed.
- `fct_daily_digest` — 26h window, `relevance_score >= 5`, top 12

**Gate before wiring concurrency:** run 5 items synchronously, read all 5 outputs yourself.
Do the scores match your judgment? Iterate the prompt until they do. If GLM's JSON is flaky
or its scores are noise, flip `ENRICH_BACKEND=claude` — that's the entire point of the
abstraction. Cost if you flip: ~$1.20/month at 60 items/day (Haiku $1/$5 per M, Batch −50%).

**Done when:** the digest table contains items you'd actually want to read.

## Phase 4 — Ship (~2h)

- `scripts/run_daily.py`, six steps in order:
  ```
  1. ingest.pipeline.run()                   fail soft per source
  2. dbt run --select staging intermediate
  3. dbt test --select int_items_dedup       HARD FAIL on duplicates
  4. enrich.run.main()
  5. dbt run --select marts
  6. deliver.telegram.send() + ledger write
  ```
  Step 3 failing hard is intentional — a duplicate bug should stop the pipeline, not ship
  a broken digest.
- `deliver/digest.py` — `build_digest()` queries `fct_daily_digest` and returns structured
  items plus run stats. **Every channel consumes this**; no channel writes its own SQL.
- `deliver/telegram.py` — MarkdownV2 requires escaping ``_*[]()~`>#+-=|{}.!`` or Telegram
  silently rejects the message. **Test with a title containing both `.` and `-`.**
  4096-char cap → chunk or truncate.
- **`raw.sent_items` ledger** — write every delivered `url_hash`, exclude it in
  `fct_daily_digest`. Without this the 26h overlap resends yesterday's top item, which is
  the fastest way to stop trusting the digest.
- **Always send, even on quiet days.** Fewer than 3 items → send the count plus the top
  sub-threshold items. Silence is indistinguishable from a crashed job.
- BigQuery target: datasets `ai_radar_raw` / `ai_radar_marts`, partition on
  `DATE(published_at)`, cluster on `source_name`. Service account needs
  *BigQuery Data Editor* + *BigQuery Job User*.
- Actions workflow with `workflow_dispatch` (test without waiting), 30-min timeout,
  `if: failure()` Telegram alert. Cron is **UTC only and ignores DST** — `0 5 * * *` is
  07:00 Paris now, 06:00 after late October.
- **Test the failure path on purpose** — break something, confirm you get told.

**Done when:** you wake up and it's already there.

## Phase 5 — Email + web archive (~2h)

Both channels reuse `build_digest()` from Phase 4. Neither touches the pipeline.

**Gmail SMTP (`deliver/email_smtp.py`)**

- Enable 2-Step Verification on the Google account, then generate a 16-char **App Password**
  for "Mail". Google shows it once. Store as `GMAIL_APP_PASSWORD`.
- `smtplib.SMTP_SSL("smtp.gmail.com", 465)`, login with the address + app password, send a
  `MIMEMultipart("alternative")` with a plain-text part and an HTML part.
- Render the HTML from the same Jinja template as the site so the two never drift.
- **Known fragility:** the app password dies if the account password is rotated or 2FA is
  reconfigured. Treat an SMTP auth failure as a warning in the Telegram footer, not a
  pipeline failure — Telegram remains the channel of record.

**Static site (`deliver/site.py` → GitHub Pages)**

- Render `site/index.html` (latest digest + links to previous days) and `site/YYYY-MM-DD.html`
  per day, from `fct_items` rather than only today's window so the archive is complete.
- Commit the `site/` output to a `gh-pages` branch from the daily workflow
  (`peaceiris/actions-gh-pages` or a plain `git` push with the workflow token). Enable Pages
  on that branch in repo settings.
- Keep it genuinely static — no JS calling BigQuery, no API keys in the page. The build has
  the credentials; the published page must not.
- Plain semantic HTML with a small inline stylesheet. Readable on a phone. No framework.
- This URL goes in the README and on the CV. It is the "it's actually running" evidence.

**Done when:** the digest arrives on Telegram *and* in Gmail, and the Pages URL shows today
plus every prior day.

## Phase 6 — Calibration (2 weeks, 5 min/day)

The step everyone skips, and the one that decides whether you're still reading this in
month three. Log which items you actually click; retune `profile.yaml`, source weights, the
`0.30` decay constant, and the threshold. Add the category diversity cap (max 4 per
category) so a busy arXiv day doesn't produce 12 papers and no tooling news. Prune sources
that never land an item.

## Known risks

| Risk | Mitigation |
|---|---|
| Feed URLs rot (certain) | `validate_feeds.py` weekly; alert on 7-day silence per source |
| Reddit tightens OAuth further | Fail soft; it's one source of fourteen |
| GLM free tier rate-limits or returns bad JSON | Log the failure rate; flip `ENRICH_BACKEND=claude` |
| Duplicates escape canonicalization (high initially) | dbt `unique` test as a hard gate; every escape becomes a test case |
| Actions cron skips a run | The 26h window makes the next run self-healing |
| Gmail app password revoked by a password rotation | SMTP failure warns in the Telegram footer; Telegram stays the channel of record |
| A credential leaks into the published Pages HTML | Site render takes only `build_digest()` output; verify the page opens offline |
| **You stop reading it after 3 weeks** | One message, ruthless threshold, kill dead sources. Every design choice above exists to protect against this. |
